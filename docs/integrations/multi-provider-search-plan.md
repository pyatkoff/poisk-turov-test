## Ближайшие полезные пакеты P1

- Выполнено в #1716, опубликовано на f690ff035964a1debf3d03ed7e63c33f715f2aa9: устранено постоянное обрезание point-TV выдачи после20; локальное раскрытие

  сохранённому набору, раскрытие сохраняется при сортировке и сбросе фильтров,
  новый поиск очищает старое раскрытие. Общий supplier-response cap не менять.
- Довести путь выбора отдельного point-предложения: его searchId/offer identity
  сохраняются вместе с источником, не заменяют исходный поиск. Нельзя делать
  такие строки кликабельными до проверки контекста во всём пути выбора.
  Existing lead transport/field mapping не менять; это отдельный согласованный пакет.
- Единый локальный фильтр/сортировка оценивают конкретное подходящее предложение,
  а не минимум одного тура и питание другого. Сбой/задержка одного источника
  не скрывает результат остальных. Старое поколение поиска не смешивается с новым.
- Полноту показывать по каждому источнику: pending/complete/partial/unavailable
  и фактический диапазон дат. Количество отелей считать по принятым local ID;
  предложения и минимумы разных источников не объявлять одинаковыми пакетами.

## Общая модель — контракт приложения, не предполагаемые поля API Андромеды

| Сущность | Инвариант |
| --- | --- |
| Отель | catalog_hotels.id плюс отдельная принятая связь provider + hotel ID; совпавшие числа разных API не равны |
| Предложение | provider + непрозрачная ссылка предложения + supplier search context + поколение общего поиска |
| Источник и оператор | Разные поля: тур ANEX через Tourvisor остаётся источником Tourvisor |
| Условия | Даты, ночи, взрослые и возраст детей; номер, размещение, питание, валюта и компоненты цены сохраняются раздельно |
| Цена | Decimal amount, валюта, minimum/concrete/quote и статус включения сборов; unknown не превращается в ноль |
| Полнота | Фактические дата-окно/страница/курсор и состояние источника; недоступность не равна no_offer |
| Контент | Описание/фото имеют своё происхождение, независимое от источника цены |
| Жизненный цикл | Отмена/новое поколение инвалидируют старые результаты и выбор; восстановление не меняет supplier search context |

Использовать действующую нормализацию anex-normalizer.php и принятый resolver
anex-search-mapping-registry.php с manual precedence/pair exclusions.
Hotel-identities.php остаётся pilot JSON registry, не универсальным live-хранилищем.
Общий provider/offer/search contract ниже целевой: текущая public ANEX projection
ещё не несёт полного offer identity/search context для выбора. Не обобщать ANEX-специфичные
поля или SQL-таблицы наугад. Для каждого подключённого источника — один адаптер
перевода критериев/ответов и проверка контрактных примеров. Общие карточки,
фильтры и выбор принадлежат одному актуальному UI-владельцу.
Не добавлять третий независимый renderer/skin поверх двух существующих.

При фактическом добавлении третьего источника убрать допущения вида «оба»:
карточка хранит набор источников, фильтр «несколько источников» означает >=2.
Вклад источника в минимум и количество считается из предложений после фильтров.
Сейчас отключённую Андромеду не показывать как подключённую или ошибающуюся.

## Порядок подключения Андромеды

1. Получить точный официальный API-контракт и разрешённый read-only доступ.
   Уточнить справочники отелей/географии, дату-окно, пакет hotel IDs, пагинацию,
   асинхронный поиск, валюты, пересчёт/доплаты и лимиты. Не переносить на неё
   ANEX HOTELS30/7дней/10r/s/60r/min.
2. Сохранить ограниченную контрольную выборку реальных ответов с provenance,
   убрать секреты. Адаптер пока выключен; нет новых bookings или массового обхода.
3. Связать hotel IDs контрольной выдачи с нашей базой по строгим доказательствам.
   Не применять название/цену как единственный критерий и не менять manual decisions.
4. Подключить нормализованный результат к общему хранилищу одного поколения поиска,
   сохраняя состояние/лимиты/таймауты каждого источника. Фильтры и «Показать ещё»
   не вызывают сеть; поиски выполняются по явному действию и в проверенном бюджете.
5. На одном ограниченном preview проверить три источника: одинаковые числовые ID
   разных API, общая карточка, задержка/ошибка одного источника, новые критерии,
   фильтры, раскрытие и возвращение из выбора. Сопоставление и цена не выдумываются.
6. Только после этого — отдельная интеграция в актуальную общую release с её
   владельцами и isolated provenance. Production approval остаётся отдельным.

Конкретный supplier access/credentials запросить только перед этапом1,
после подготовки списка обязательных методов. Сейчас P1/P2 могут продолжаться
без доступа к Андромеде. Токены и другие секреты хранить только через существующий secrets-механизм, не копировать в чат или публичный Git.
