# AnyTour — Андромеда: план до рабочего выбора тура

Актуализация 2026-09-10 принятого [плана #1832](https://github.com/pyatkoff/poisk-turov-test/pull/1832).
Задача — [#1717](https://github.com/pyatkoff/poisk-turov-test/issues/1717), только
`pyatkoff/poisk-turov-test`. Цель: в актуальном общем тестовом поиске пройти
**отель → варианты → подробности → выбор конкретного тура → проверка состава/цены →
явное принятие изменившейся цены → существующая форма заявки → возврат**.
Настоящая отправка заявки и production не входят в этот результат.

## Зависимости и приоритет

A1 сохраняет уже принятый saved-details baseline и проверяет совместимость текущих
UI/API при handoff, а не возвращает задачу к началу интеграции. **A2 (SEARCH) и A3 (INT)
готовятся параллельно на непересекающихся paths; A4 объединяет их результаты.**
A5 исправляет только подтверждённые остаточные дефекты. A6 принимает составную версию.
Не ждать свободного UI ради серверной работы; не подменять независимую работу новым
renderer, массовым поиском или повторным отчётом «передал».

### A1. Совместимость актуального общего превью

**Владелец:** единственный SEARCH writer; INT передаёт API evidence и ограниченный diff.
1. Сопоставить текущее опубликованное UI, установленный API/module и retained context.
   Сохранить #1830/#1831 и последующие исправления, не повторять уже завершённые PR.
2. Eligibility берётся только из удержанных provider pages; detail-кнопки без полного
   пригодного контекста отсутствуют. Новый поиск сбрасывает раскрытие, возврат сохраняет
   свой отель/список. Single-hotel layout занимает основной столбец без лишнего filter rail.
3. Если объединённая версия уже опубликована и её identity/readback совпадают, не делать
   новый build/deploy ради записи в плане. При необходимом runtime/UI изменении — узкая
   совместная проверка, одна сборка и штатная exact-публикация SEARCH.

**Выход:** URL + UI source/artifact + API source/module + deploy/readback; узко проверенный
путь варианты → подробности → закрыть/повторно открыть → возврат на этой версии.
Повторное чтение сохранённого detail не запускает supplier search; фильтры/сортировка
не теряют удержанные варианты. Непроверенные ветви и mobile явно deferred.
Старый/unknown контекст не replay; новый обычный поиск допустим только как отдельно
зафиксированная соразмерная приёмка изменённого поведения, не замена потерянного checkpoint.

### A2. Один владелец выбранного тура

**Владелец:** SEARCH; переиспользовать опубликованную серверную опору #1873/#1846.
1. Один selected-tour owner удерживает `provider/operator/offer_ref/search_ref/generation/
   page/hotel_scope` от явного выбора до возврата. Цена, имя, local_id или порядковый
   номер карточки не заменяют identity. Сырой `supplier_offer_id` остаётся приватным.
2. В момент действия использовать существующий серверный lookup/current mapping check.
   Истёкший, удалённый, переотнесённый или относящийся к другому поиску вариант отклоняется.
3. Ответ применяется только к всё ещё выбранной identity и актуальному действию:
   поздний ответ A после выбора B не меняет B; новый поиск инвалидирует старые ответы.
4. Возврат восстанавливает своё раскрытие, локальные фильтры/сортировку и доступные
   страницы. Ошибка Андромеды не сбрасывает данные Tourvisor/ANEX.

**Узкая приёмка:** равная цена у разных операторов; быстрые A→B клики; поздний ответ;
новый поиск; истечение/revoked mapping; возврат без нового supplier запроса.
**Выход:** выбран конкретный сохранённый тур, но цена поиска ещё явно непроверенная.
Не создавать третью панель, renderer, отдельного владельца selection или новые credentials.

### A3. Реальный пакет и честная проверка цены

**Владелец:** INT. Не переписывать готовый CLI bridge #1883.

**A3.0 — готовая опора, не новая задача.**
`app/integrations/andromeda-saved-package-runtime.php` уже содержит
`anytour_andromeda_capture_saved_package`: существующие PackageCapture/OfferStore/client,
private auth, search lock, atomic write/readback и месячный счётчик. Повтор captured
читается локально; reserved/unknown/stale не перевыполняются. Пакет остаётся приватным.
Зависимости #1846 закреплены на `7c3c5bb55c88e376d97c998d0ba77a46960584d6`;
совместимость проверялась с установленным runtime `95fa11f5a1cb7e18c905c9760a1eae7f2c0ee7aa`
и API #1873. До invocation проверить наличие полного необходимого приватного набора,
не считать один файл bridge достаточным и не merge целиком drafts #1833/#1846.

**A3.1 — конкретное приватное подключение и один реальный capture.**
- Связать уже готовый bridge с текущим accepted-mapping reader и существующим
  package-enabled transport через разрешённый private invocation. Зафиксировать exact
  source/dependencies/файлы/способ запуска/эффекты; не строить второй клиент или launcher.
- Проверить разрешённость именно метода/пути запуска. Использовать имеющийся preview
  допуск без повторного запроса пароля. Допуск публикации #1878 не считать разрешением
  менять main или запускать новый capture launcher: для выхода за границу нужен
  конкретный отдельный handoff, а не обход или повтор отказа.
- Использовать один явно выбранный действующий retained offer и исходный контекст.
  Нет пригодного context — `expired`/blocked, а не новый PRICE или first-row fallback.
- До сети — durable reservation/readback, текущие mapping/session/source и бюджет.
  В текущем bridge разрешён **не более одного `broninit`**, без login/PRICE/calc/flights.
  Unknown/неполный результат сохранить и не replay; смена source не отменяет checkpoint.
- Raw claim/source envelope хранить только приватно. В issue/артефакт — очищенная
  квитанция, digest и классификация результата; не claim, sid, credentials или личные данные.

**Выход A3.1:** реальный сохранённый ответ и доказательство связи конкретного
`PRICES.id → claiminc` с выбранным offer. До этого identity/package/quote не объявлять
проверенными. Приватное сохранение ответа само по себе не подтверждает эту связь.

**A3.2 — публичная проекция по фактическому образцу.**
Сначала проверить identity/структуру/предупреждения сохранённого ответа; затем fixture
и allowlist: отель, номер, размещение, питание, даты, состав туристов без персональных
данных, подтверждённые услуги/рейсы и явно известные цена/валюта. Отсутствующее поле
остаётся неизвестным, а не придуманным. Полный claim и себестоимость клиенту не отдавать.
`buyerMoneys[].buyerClaimMoney[].net` — цена туриста;
`moneys[].money[].net` — себестоимость. Общий extract-net/fallback между ними запрещён.
Цена поиска, сумма из пакета и результат актуализации — разные факты; неизвестные доплаты
не обнулять и внешнюю price arithmetic не менять.

**A3.3 — отдельная актуализация, не побочный эффект capture.**
`broninit` получает пакет; `get_flights` относится к внешним перелётам при
`freightExternal>0`; `calc` пересчитывает переданный claim. Эти методы не взаимозаменяемы.
Текущий #1883 не вызывает flights/calc: перед расширением проверить существующий код,
официальный контракт и допускаемые эффекты каждого метода. Для необходимой операции —
отдельная bounded reservation через существующий счётчик, без автоматического replay.
Не выполнять `bron`/`bron_ticket`, реальные заявки, фиктивных туристов и операции с
неопределённым эффектом. Требование реальных персональных данных блокирует этот шаг.
Один HTTP success/calc не означает гарантированную доступность/финальную цену:
сохранять фактические warnings/errors, валюту, время проверки и привязку к выбранному туру.

**Приёмка A3:** реальный очищенный образец + узкие fixtures по identity, buyer/cost,
malformed response, недоступности, изменению цены, истечению и late/unknown no-replay.
**Выход:** достоверная публичная проекция конкретного пакета и честное состояние
проверки цены; не booking и не новый поисковый запрос.

### A4. Проверка → согласие с ценой → существующая форма

**Владелец:** один SEARCH UI writer по INT handoff. Зависимости A2 и применимая A3.
1. Согласовать состояния с существующим owner: выбран/не проверен → проверяем →
   подтверждён / цена изменилась / недоступен / контекст истёк / не удалось проверить.
   Unknown не маскируется под отсутствие тура; старая цена не выдаётся за проверенную.
2. Новую цену принимать явно для конкретной identity и версии проверки. Если сумма,
   валюта, состав или выбранный тур снова изменились, прежнее согласие недействительно.
3. Один контекст и одна согласованная сумма во всех шагах, включая preview формы
   заявки и возврат. Повторный клик/поздний ответ не создают дубль и не подменяют выбор.
4. Переиспользовать существующий lead transport/field mapping без изменения. Если
   текущий контракт не передаёт источник безопасно, подготовить точный пример текущих
   полей, несовместимость и минимальный diff для отдельного согласования. Не маскировать
   Андромеду под Tourvisor и не посылать сырой supplier ID.

**Выход:** связный тестовый путь до существующей формы; реальные отправки отключены
существующим guard, включая мессенджеры. Ошибка проверки не отправляет заявку.
Изменение внешнего контракта/транспорта и реальная отправка не разрешены этим этапом.

### A5. Только подтверждённые остаточные дефекты

**Владельцы:** INT/SEARCH на непересекающихся paths; не создавать новую очередь интеграции.
- Сначала проверить готовую реализацию grouped pages, hotel expansion, retention,
  счётчика и observations. Нет воспроизводимого пробела — не менять рабочий код.
- Публичные предложения — с accepted local_id. Несопоставленные из обычного ответа
  сохраняются существующим observation механизмом вместе с пришедшими названием,
  описанием/фото и provenance. Без новых supplier content запросов и без matching.
- Partial/error следующей страницы сохраняет прежние страницы и другие источники.
  Локальные фильтры/сортировка/повторное чтение не стартуют поиски; пустой результат
  отличается от ошибки. Полноту доказывать фактическими страницами, не числом карточек.
- Наблюдавшиеся общий failure-banner над заполненной выдачей и незагруженное фото
  не доказывают причину сбоя поставщика. Общий renderer/error handler остаётся SEARCH;
  INT исследует только доступное сохранённое source evidence, без replay поиска.
- Для изменённого сценария достаточно фактического времени до первой полезной карточки,
  завершения страниц и числа запросов; массовые проходы/произвольные нагрузочные тесты
  не входят в #1717. ANEX через Андромеду — начальный сценарий, не отдельное ANEX API.
  Если штатный control не даёт ANEX, честно записать all operators, не подменять payload.

**Выход:** исправлен конкретный дефект либо сохранено доказательство, что нужная защита
уже работает. Catalog/manual/bindings и обычные сохранённые observations не переписаны.

### A6. Совместная приёмка и release handoff

**Владелец:** координатор SEARCH; INT передаёт ограниченный пакет и доказательства.
Принять A1→A2→A3→A4 на одной точной составной версии общего превью: desktop/mobile,
промежуточная ширина затронутой области, возврат, partial/error/expired/changed-price,
сохранность TV/ANEX и отсутствие реальных отправок. Физический Safari отдельно:
эмуляция не является проверкой устройства; непроверенное явно deferred.

**Handoff:** URL; fresh release SHA; точный список source/dependency файлов; API/UI
source и artifact digest; checks; deploy/readback; noindex/lead/analytics guards;
подтверждённые сценарии и deferred; существующая проверенная rollback-точка и условия
отката. Не публиковать whole-site artifact старой ANEX-основы и не merge #1493 целиком.
Если общий preview уже соответствует этому exact пакету, повторная публикация не нужна.

**Граница завершения:** итоговая preview-приёмка передана владельцу, блокеры названы;
после разрешённых A1–A6 приостановить именно этот автопилот. Production/main/#1334
требуют отдельного одобрения конкретной версии. Не держать автопилот в бесконечном
ожидании production gate и не переключать соседние задачи/расписания.

3. При блокере записать операцию, причину, известный эффект, exact checkpoint и
   разрешённый независимый пакет. Не повторять отказ/unknown и не обходить права.
   Недоступен live A3 — остаются saved-response contract/fixtures либо подтверждённый A5;
   нет необходимых данных — честный blocked, не выдуманный образец или фиктивный тест.
4. Обновить одну текущую строку INT #1717, предметный audit и #1717; handoff/claim в #996.
   Сохранять source/PR/checks/published/deferred и неизвестные checkpoints.
5. Продолжать следующий безопасный связный пакет в текущем запуске. Сообщать только
   новое полезное изменение/существенный блокер. Один отказ не выключает всю задачу.

## Модель и ограничения настройки

Следующий блок — сохранённая рекомендация принятого #1832, не новая проверка
доступности инструментов. Эта актуализация не меняет модель, prompt или расписание.

Основная рекомендация: GPT-5.6 Sol, high для API/context/связанной реализации.
GPT-6 Astra high — для неоднозначного денежного/API контракта или сложного
согласования; max/ultra не нужны для каждого пакета. Это инженерное назначение,
не измерение стоимости/квот аккаунта. Модель не заменяет checks/provenance.

Официальные описания [моделей](https://learn.chatgpt.com/docs/models) и
[scheduled tasks](https://learn.chatgpt.com/docs/automations?surface=app) сверены.
Доступный automations.update поддерживает prompt/schedule/enabled, но не model или
reasoning_effort; peek не возвращает фактическую модель. Поэтому запись рекомендации
не означает её переключение. Не утверждать «Sol high установлен» без настройки/readback;
