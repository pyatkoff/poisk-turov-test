# AnyTour — Андромеда: план до рабочего выбора тура

Обновлено по поручению владельца 2026-09-09. Задача [#1717](https://github.com/pyatkoff/poisk-turov-test/issues/1717).
Цель: в актуальном общем тестовом поиске найти отель, раскрыть варианты Андромеды,
посмотреть и выбрать конкретный тур, проверить его состав/цену и подготовить
корректный переход к существующей заявке. Разработка в этом направлении не включает
сопоставление отелей, сбор новых связей или очередь #1759.

- Этот документ задаёт порядок и приёмку. Одна текущая строка INT #1717 в
  [scoped плане](anex-search3-autopilot.md) и свежие комментарии #1717 содержат
  следующий исполняемый шаг; release current_task принадлежит SEARCH.
- Серверный INT: короткие ветки от свежей feature/anex-search-adapter-20260907.
  Общий UI: короткие ветки от свежей release/search3-production-ready-v1
  только после передачи точных paths в #996. Две существующие основы сохраняются.
- Нельзя брать занятый renderer/provider только потому, что прошло время. Проверить
  текущий PR/CI/исполнителя. При активном SEARCH writer продолжать независимую INT часть.
- История commits/reports сохраняется. Старые этапы auth/catalog/matching не новая очередь.

## Пакеты разработки и проверяемый результат

### A1. Завершить публикацию общей выдачи и подробностей — первый приоритет

**Владелец:** текущий SEARCH writer; INT передаёт diff и API evidence. Зависимости #1830/#1831.
1. Совместить eligibility по реально удержанным страницам провайдера с detail state.
   Не показывать неработающие кнопки на строке только с provider=andromeda.
2. Сохранить reset раскрытия при новом поиске и раскрытие при возврате к старой выдаче.
3. Сохранить исправление single-hotel desktop layout в действующем CSS owner.
4. Пересобрать generated assets/runtime из объединённых исходников, не выбирать
   один из конфликтующих generated файлов целиком.
5. Узкий совместный browser-сценарий, обязательные CI, одна штатная публикация
   exact artifact в /_preview/search3-site-candidate/. Автор публикации один.

**Приёмка:** accepted local hotel → варианты → подробности конкретного номера →
закрыть/снова открыть → фильтр/сортировка/возврат. Удержанные предложения не исчезают,
повторное открытие деталей не вызывает сеть; новый поиск убирает старый контекст.
На mobile/desktop нет overflow и узкой карточки вместо основного столбца.
Noindex, disabled production leads, counter0, provenance и rollback подтверждены.
**Результат для владельца:** конкретная ссылка общего превью и проверенный сценарий.
Физический Safari не объявлять проверенным без проверки устройства.

### A2. Состояние выбранного предложения и возврат

**Владелец:** SEARCH по согласованному INT контракту. Зависимость A1 для UI-приёмки.
1. Использовать существующий selected-tour owner; не создавать третью панель/renderer.
2. Удерживать provider, operator, offer_ref, search_ref, generation, page и hotel_scope.
   Сырой supplier_offer_id остаётся на сервере; цена/имя/local_id не заменяют offer identity.
3. По явному выбору проверять текущий контекст через существующий приватный lookup.
   Смена критериев/истечение сессии/удалённый вариант инвалидируют выбор.
4. Возврат сохраняет фильтры, список и раскрытый отель. Ошибка Андромеды не сбрасывает TV.

**Приёмка:** два равных по цене предложения разных операторов не смешиваются;
быстрые A→B клики и поздний ответ A не подменяют B; после нового поиска старый
выбор не восстанавливается. Пока quote не готов, просмотр выбранного варианта
не означает подтверждённую цену или разрешённое бронирование.
**Результат:** можно осознанно выбрать конкретный вариант и вернуться в выдачу.

### A3. Получить состав выбранного пакета и проверить цену

**Владелец:** INT. Независимая серверная подготовка может идти во время A1.
1. Переиспользовать существующие client/store/HTTPS/сессию, не вводить второй API client.
   Добавлять только документированные методы и только после проверки их эффектов.
2. Подготовить один ограниченный запрос получения пакета для явно выбранного
   сохранённого offer. Подтвердить связь PRICES.id → claiminc на реальном ответе;
   не выводить ID из имени, hotelKey, фото или хэша.
3. До внешнего запроса сохранить reservation и exact source; после — очищенный
   raw response/digest и readback. Не переигрывать unknown и не запрашивать свежий поиск
   ради замены отсутствующего checkpoint.
4. broninit получает пакет; get_flights предусмотрен при freightExternal>0;
   calc пересчитывает переданный claim. Не вызывать bron/bron_ticket или создавать заявку.
   Семантику конкретного разрешённого capture проверить до выполнения; неопределённый
   эффект метода блокирует только этот live шаг, а не offline реализацию.
5. Проецировать только публичные поля: отель, номер, размещение, питание, даты,
   туристы, подтверждённые рейсы/услуги и корректную валюту/цену.
   Полный claim, credentials, документы туристов и себестоимость не отправлять в браузер.

**Контракт цены:** buyerMoneys[].buyerClaimMoney[].net описан как сумма для туриста;
moneys[].money[].net — себестоимость агентства. Общий extract-net запрещён.
Сохранить цену поиска и проверенную цену раздельно; неизвестные доплаты не обнулять.
Не обещать final/available по одному успешному HTTP или calc; сохранить warnings/errors.
При необходимости реальных личных данных не подставлять фиктивных туристов.

**Приёмка:** один реальный очищенный образец, tests по нему, изменившаяся цена,
недоступный пакет, malformed response и stale context. Без supplier booking.
**Результат:** достоверный состав конкретного тура и честное состояние проверки цены.

### A4. Подключить проверку к выбору и существующему сценарию заявки

**Владелец:** SEARCH + INT handoff, один UI writer. Зависимости A2/A3.
1. Состояния: проверяем → доступен / цена изменилась / недоступен / не удалось проверить.
   Старая цена остаётся подписанной; новую цену пользователь принимает явно.
2. Сохранить один provider-qualified контекст до summary и перехода к форме заявки.
3. Проверить совместимость с действующим lead transport/field mapping. Если контракт
   не умеет безопасно передать источник, подготовить конкретный diff/пример для
   отдельного согласования, а не маскировать Андромеду под Tourvisor.
4. На превью отправка настоящих заявок отключена. Сценарий мессенджеров проверять
   существующими заглушками/guard, не отправлять реальную заявку менеджеру.

**Приёмка:** одна и та же identity/даты/состав/согласованная сумма во всех шагах;
ошибка проверки не отправляет заявку, повторный клик не создаёт дубль.
**Результат:** завершённый тестовый путь от выдачи до подготовленной заявки.
Изменение внешнего транспорта и реальная отправка требуют действующего отдельного допуска.

### A5. Полнота, скорость и наблюдения — только полезные остаточные дефекты

**Владелец:** INT/SEARCH на непересекающихся paths. Не задерживает A1–A4.
- Сначала проверить существующий код: grouped pages, hotel expansion, месячный
  счётчик, сохранённые страницы и observations уже реализованы частично/полностью.
  Исправлять подтверждённый пробел, не строить повторно.
- Публичные карточки Андромеды показывают предложения с принятым local_id,
  используют существующий локальный контент; missing media обрабатывается честно.
- Несопоставленные из обычной выдачи сохраняются в существующей очереди наблюдений
  с provider/operator IDs, исходным названием, условиями, временем, ссылкой на фото,
  описанием если оно действительно пришло, и provenance. Без нового supplier content
  запроса, без автопринятия links и без возвращения этого чата к matching.
- Отдельные статусы источников и страниц: complete/partial/error. Сбой следующей
  страницы сохраняет предыдущие; пустой ответ не означает ошибку.
- Измерить время до первой полезной карточки, завершение фактических страниц,
  количество HTTP и повторные запросы на одном изменённом сценарии. Не устраивать
  массовое тестирование 91 страны/всех операторов. Начальная приёмка — ANEX через
  Андромеду; Интурист/FUN&SUN/Библио-Глобус расширять отдельно по готовому контракту.

**Приёмка:** локальные фильтры/сортировка/повторное чтение не вызывают supplier;
сохранённые наблюдения переживают запрос, catalog/manual/mappings не меняются.
**Результат:** прозрачная полнота выдачи и очередь на будущее без потери данных.

## Модель и ограничения настройки

Основная рекомендация: GPT-5.6 Sol, high для API/context/связанной реализации.
GPT-6 Astra high — для неоднозначного денежного/API контракта или сложного
согласования; max/ultra не нужны для каждого пакета. Это инженерное назначение,
не измерение стоимости/квот аккаунта. Модель не заменяет checks/provenance.

Официальные описания [моделей](https://learn.chatgpt.com/docs/models) и
[scheduled tasks](https://learn.chatgpt.com/docs/automations?surface=app) сверены.
Доступный automations.update поддерживает prompt/schedule/enabled, но не model или
reasoning_effort; peek не возвращает фактическую модель. Поэтому запись рекомендации
не означает её переключение. Не утверждать «Sol high установлен» без настройки/readback;
сохранять фактическую модель запуска, если runtime её сообщает. Эта граница не блокирует
возобновление существующей задачи по новой очереди.
