### Устройство сбора

Добавляется отдельная таблица `anex_search_hotel_observations` в существующей
БД AnyTour. Единственный ключ — единый ANEX hotel ID. После успешного
нормализованного ответа первого экрана (до 300 предложений) HTTP-обработчик
сохраняет уникальные ID, название ANEX, страну AnyTour и ANEX, первую/последнюю
дату появления UTC, число поисковых ответов с отелем, последние даты вылета,
снимок local ID и SHA кода. Несколько туров одного отеля в одном ответе дают
один прирост счётчика. Это число успешных выдач, не уникальных пользователей.
IP, cookie, личности, состав туристов, токены и сырые ответы не сохраняются.

Одна атомарная операция upsert на ответ; first_seen не перезаписывается,
порядок ID одинаков для конкурирующих записей. Пустой/ошибочный ответ не
создаёт отели. Сбой сохранения не ломает поиск, но даёт фиксированный
серверный код и виден при проверке. Дополнительных запросов ANEX нет.
DDL выполняется только существующим isolated-preview deploy до переключения
каталога; HTTP никогда не создаёт/не мигрирует таблицы. Повторная подготовка
таблицы не удаляет наблюдения. Старые catalog_hotels, mappings, staging и
manual decisions не меняются этим механизмом.

Очередь выводится из наблюдений с проверкой **текущего** реестра связей:
mapped — связь есть; pending — нужна обработка; manual_review — существует
блокирующее/неразрешённое ручное решение. Принятая новая связь сразу исключает
ID из pending при следующем чтении, без изменения истории наблюдений.

anex-observed-hotel-manual_review.csv. Это новая живая очередь; не подменять

### Лимиты API и пакетная проверка цен

Для выданного AnyTour токена одновременно действуют два ограничения ANEX:
не более 10 запросов в секунду и не более 60 запросов в минуту. Фоновое
обогащение через `Hotels_DETAILS` запускает запросы не чаще одного раза в
1,05 секунды. Preview-шлюз дополнительно ограничен 10 запросами в секунду и
20 запросами в минуту на серверную сессию. Перед публичным масштабированием
нужен общий для всех PHP workers счётчик токена; текущий маршрут остаётся
выключенным preview.

`SearchTour_PRICES.HOTELS` принимает до 30 идентификаторов ANEX через
запятую. Адаптер проверяет не более 30 входных ID, удаляет повторы и отправляет
один пакет. Это используется и как дополнительное доказательство для спорных
пар: ответ обязан вернуть ожидаемый `hotelKey`, а название, город, категория,
координаты, номера и питание могут усилить либо опровергнуть кандидата
ANEX → AnyTour. Наличие одинаковой цены/номера само по себе не доказывает
тождество, а отсутствие туров не опровергает его. Диагностический поиск не
принимает связь и не публикует предложение под карточкой AnyTour.

Очередь для такого прогона строит `anex_price_evidence_queue.py`. Она берёт
только строки `review` с подтверждённым `api.id == xml.id`, доступной
карточкой и кандидатами AnyTour, исключает уже найденные конфликты и группирует
по направлению пакетами максимум по 30 уникальных ANEX ID. На checkpoint

Результат имеет policy `diagnostic_only` и не содержит принятого соответствия.

Для регулярной разработки и исправлений рекомендуем Sol High. Для простого
контроля исполнения достаточно Terra Medium. Astra полезна для архитектурных
решений и отдельной проверки сложных конфликтов; постоянный Ultra для этой
очереди не требуется. Это рекомендации, не зафиксированные настройки модели
в созданном расписании: инструмент автоматизации не предоставляет такого поля.
Само получение справочников и расчёт совпадений выполняются Python/PHP без LLM.
Ни одна модель не должна принимать совпадение только по правдоподобному названию.

Официальная справка: https://learn.chatgpt.com/docs/models

## План подключения к тестовому Search3

### 1. Реестр соответствий и ручная проверка

Основной идентификатор сайта — существующий AnyTour catalog_hotels.id.
Для данного шлюза parser.anextour.ru используем единый ID отеля ANEX:
XML hotel.inc, Online Hotels_DETAILS.id и PRICES.hotelKey согласованы в
проверенных данных. Сопоставляем ANEX hotel ID → AnyTour catalog_hotels.id.
Обозначения anex_xml/anex_online в текущем коде отражают каналы получения
данных и прежние ограничения preview-реестра, а не найденное расхождение ID.
ID Tourvisor, Andromeda и других операторов по-прежнему независимы.

Проверенные факты, исправляющие прежнюю слишком категоричную формулировку:

- Снимок run 34160211233 attempt 1 / artifact 10032477127 содержит 862
  обработанных записи; у всех 830 полученных Hotels_DETAILS совпадают
  external_id == xml.id == api.id. Конфликтов ID нет; 32 записи без подробностей
  не считаются конфликтами ID.
- Для Swiss Heaven Sharming Inn Hotel подтверждена цепочка XML 5844 →
  PRICES.hotelKey 5844 → Hotels_DETAILS.id 5844. Карточка AnyTour — 453.
  Ценовая проверка: docs/integrations/anex-adapter-verified-20260907.json,
  run 34146672980; XML-запись есть в полном каталоге артефакта 10032477127.
- Эти наблюдения относятся к нашему шлюзу ANEX. Отдельный массовый проект
  сопоставления XML↔Online не нужен. Контрактный контроль согласованности
  сохранится на контрольной выборке и при получении цен; исключения будут
  диагностироваться по фактическому ответу, а не предполагаться заранее.

Сохранить решения accepted/rejected/needs_review, автора/основание, дату,
версию источника. Сделать внутреннюю карточку сравнения: название, страна,
курорт, координаты, адрес, альтернативные кандидаты, отличие корпуса.
Проверить качество автоматических правил на разных странах, коротких
названиях, переименованиях и отельных комплексах. Принятые решения человека
не перезаписывать следующей выгрузкой. Ввести отдельные повторные запросы
для временных ошибок; затем отдельный поиск кандидатов для unmatched.

Результат этапа: небольшой проверенный Online-набор, пригодный для пилота.
Не требуется ждать сопоставления всего каталога, чтобы начать тестовую интеграцию.

### 2. Использовать единый ID ANEX и доделать серверный адаптер

Текущая компактная таблица содержит 8734 предварительные XML-связи,
а её загрузчик пока технически разрешает только anex_xml. В пилотном реестре
пять проверенных связей уже имеют одинаковые ID в обоих каналах.
В задаче S3-ANEX-01 нужно научить адаптер цен использовать принятую связь
ANEX → AnyTour независимо от канала XML/Online, сохранив совместимость
существующих меток источника. Ограничение загрузчика — задача нашего кода,
а не свидетельство различающихся ID у поставщика. Статус принятия связи
с AnyTour остаётся отдельным условием: одинаковый ID внутри ANEX не доказывает
правильность выбранного отеля в нашей базе.

Проверить критерии поиска по собственным справочникам ANEX: город вылета,
страна, отели, валюта, состав туристов. Не использовать числовые ID Tourvisor.
Подготовить HTTP-контроллер и ограниченное серверное хранение поисковой
сессии: текущий PHP-класс хранит группы/предложения только в памяти.
Клиент получает непрозрачные ключи, токены и supplier-state остаются на сервере.
Добавить обработку отложенного поиска и пагинацию: сейчас PRICEPAGE=1,
полученный searchKey ещё не опрашивается до завершения.

Результат: поиск, раскрытие предложения и получение деталей работают
через стабильный серверный контракт на подтверждённом наборе отелей.

### 3. Пилот в существующем тестовом интерфейсе

Проверить свежую активную ветку release/search3-production-ready-v1 и
согласовать места изменения с действующей разработкой Search3. Использовать
отдельную ветку и выключенный по умолчанию флаг ANEX для изолированного preview.
Существующие presentation-модули и Tourvisor-контракт сохранить.

Одна карточка отеля AnyTour объединяет предложения источников. У предложения
раздельно хранить источник и туроператора: Andromeda тоже может дать ANEX.
Загрузка, тайм-ауты и ошибки поставщиков независимы. Дедупликация предложений
учитывает даты, ночи, состав туристов, номер, питание, перелёт и происхождение
цены; одинакового названия отеля или оператора недостаточно.

Результат: на небольшом проверенном наборе в тестовом Search3 видны реальные
предложения ANEX, выбор и раскрытие не ломают существующие предложения.

### 4. Проверка цен и пути выбора тура

Проверить исходную и пересчитанную поставщиком цену, валюту, минимум группы
против конкретного предложения, состав включённых услуг и доплаты.
Сейчас final_price_verified всегда false; финальный пересчёт пакета ещё
не подтверждён. Полноценные данные о рейсах и багаже также не доказаны.
Не выдавать предварительную цену за окончательную и не подставлять рейсы.
Учесть возраст детей; текущие ограничения infants документировать до поддержки.

Приёмка: одинаковые критерии в ANEX и Search3, правильная цена и состав тура,
работающие фильтры/сортировка/раскрытие, отсутствие неверного объединения
отелей, корректное поведение при недоступном ANEX. Проверить мобильный путь
до тестовой заявки без отправки реальной заявки. Изменения защищённого
механизма доставки заявок требуют отдельного согласованного решения.

### 5. Расширение покрытия и другие источники

После успешного пилота расширять набор стран/отелей принятыми соответствиями,
включить обновление справочников и контроль устаревших связей. Добавить
Andromeda отдельным адаптером после получения доступа и подтверждения API.
Существующий Tourvisor остаётся самостоятельным источником.

Публичное включение, production и миграция не следуют автоматически из
зелёного CI. Для тестового preview нужны согласованный кандидат, проверка
изоляции, отсутствие production-заявок/аналитики и возможность отключить ANEX.
