## SEARCH-01 — закончить текущую приёмку

- Польза: читаемое описание и проверенный путь от формы до возврата в выдачу.
- Работа: принять результат текущего entities PR, затем закрыть только оставшиеся
  mobile/Safari/переходы, которые ещё не проверены на опубликованном source.
  Перед взятием любого файла — свежие #996/PR/current_task.
- Компоненты: canonical `v2/tour-controller-v4.js` у объявленного владельца;
  generated manifest и source hashes меняются вместе по существующей процедуре.
- Готово: текст безопасно отображается без буквальных сущностей и HTML execution;
  исходный tour/lead payload сохранён; narrow hostile-entity regression зелёный.
  Safari, который физически не проверяли, остаётся deferred.
- Выход: source PR + релевантный audit, без повторного полного live-поиска ради отчёта.
  Откат — предыдущий checked source/artifact при обнаруженном регрессе.

## SEARCH-02 — один контекст конкретного предложения

- Польза: цена, номер, питание и источник выбранного тура не подменяются соседним туром.
- Входы: сохранённые broad TV, point-TV и ANEX raw/projected fixtures; текущий selected
  и внешний lead contract. INT отвечает за source identity, SEARCH — за UI-состояние.
- Описать внутренний envelope: generation, provider, providerSearchId, offerKey,
  supplierHotelId, acceptedLocalHotelId, criteria snapshot, observedAt, price/currency,
  условия пакета и признак неизвестных сведений. Это проектируемые внутренние поля;
  реальные имена и доступность подтверждаются источником, не выдумываются.
- Отдельно: общий broad searchId остаётся своим; point searchId принадлежит только
  point-оферам. Недоступное offerKey нельзя заменить hash от похожей цены и объявить
  бронируемым идентификатором. Источник API отдельно от туроператора.
- Готово: таблица legacy→internal полей, неизвестные поля, immutable fixture, правила
  возврата/new generation/expiry и принимающий owner. Ничего не записано в внешний lead.
- Проверка: одинаковые числовые ID разных источников не коллидируют; offer identity
  не меняется от сортировки/фильтра, ответ старой generation игнорируется.

## SEARCH-03 — выбор тура из явной проверки TV

- Вход: SEARCH-02. Own addon `v2/anex-search3-preview-v1.js`, existing point handler;
  shared selected owner только после claim #996. Реализация в одном связанном пакете.
- Сохранить source-specific searchId и выбранный tour identity до selected и обратно;
  broad state и его 58/100/другое реальное число исходных отелей не перезаписывать.
- Использовать существующий TV selection путь лишь если он поддерживает этот контекст.
  Если требуется изменение внешнего lead mapping/transport — подготовить конкретный
  diff и отдельный допуск; до него point остаётся comparison-only.
- Приёмка: выбрать point-тур A, изменить допустимый вариант, вернуться, выбрать broad B;
  A и B сохраняют свои ID/параметры/цены, чужой searchId не уходит в handoff. Новый поиск
  инвалидирует старые действия. Реальных заявок тест самовольно не отправляет.
- Fixture-тесты: point success/loading/empty/timeout/stale, filtered reveal, двойной click.
  Network budget прежний: 1 start/hotel, max3/generation, 1 in-flight, 8 polls с интервалом 7,5 с и deadline 60 с;
  render/filter/reveal не создают запросов. Live — только если остался конкретный риск.
- Откат: отключить новый выбор прежним comparison path, сохранить полученные предложения.

## SEARCH-04 — выбор ANEX и состав цены

- Вход: INT сохраняет доказанный offer/search context и поля цены; состав доплат
  проверяет отдельный владелец #1685. Отсутствие ответа не превращать в «всё включено».
- Компоненты: INT `v2/api-anex-search3-preview.php`; SEARCH выбранный тур/summary.
  Один writer на стыке, без правок защищённой арифметики.
- Показывать источник, оператора, даты, ночи, туристов, номер, питание и цену именно
  выбранного предложения. Min карточки не копировать как цену каждого тура.
- Неизвестные рейсы/багаж/топливо/finality явно неизвестны. Если существующий путь
  умеет только консультацию, не называть её подтверждённым бронированием.
- Готово: поддерживаемый owner-approved handoff с тем же provider/offer; либо честный
  ограниченный просмотр с зафиксированной причиной недоступности выбора. Второй исход
  не закрывает весь пакет как готовое бронирование.
- Узкие проверки: source collision, different meals/rooms, missing facts, expired offer,
  new generation; визуально selected/return и длинная цена на mobile/desktop.

## SEARCH-05 — единый тестовый поиск

Это принимающая часть INT-12: один общий PR/owner и один цикл приёмки, не два переноса.
INT-06 и SEARCH-02/04 — producer/consumer одного контракта, без двух конкурирующих DTO.

- Вход: bounded INT→SEARCH handoff с exact source/destination SHA, DTO/fixtures,
  secrets boundary и supply budget. #1493 целиком не merge.
- SEARCH владеет `results-renderer-v5.js`, `runtime-v3.js`, lifecycle/continue,
  актуальными src filters и selected. INT передаёт данные/серверные зависимости.
- Портировать функцию, а не старый UI: один accepted local ID → одна карточка;
  разные provider offers остаются внутри; unbound IDs явно отдельны, без name-match.
- Вход нового провайдера проходит через один общий нормализованный контракт. Старый
  DS2 не включается. После паритета удалить перенесённые duplicate handlers/подключения,
  проверив оставшихся consumers own preview; до передачи владение addon фиксировано.
- Готово в тесте: TV-only/ANEX-only/both, source errors, no mappings, cross-generation;
  точные counts на одном наборе сохранённых входов, 0 дублей по accepted ID,
  все допустимые offers доступны. Старые результаты не считаются новым приростом.
- Публикация: fresh release exact artifact в common preview, rollback к его предыдущему
  артефакту. Интеграционный допуск не даёт production-допуска.

## SEARCH-06 — сохранность при независимом поступлении данных

- Проверять изменённый общий шов, а не переделывать уже готовые own-preview фильтры.
- Матрица: TV раньше/позже ANEX, ANEX timeout после TV success, empty, duplicate response,
  late previous generation, filter-before-complete, zero filtered offers и reset.
- Питание и бюджет применяются к одному предложению; minimum/count/calendar происходят
  от той же выборки. Неизвестный рейтинг/питание не угадывать; неполный facet не обещать.
- Готово: raw сохранён, проекция детерминирована, sorting/reveal/return не теряют туры;
  одна ошибка не обнуляет другой источник, max limits прежние, suppliercalls от фильтра0.
- Откат ограничен новой интеграционной проекцией; контракты и источники не переписывать.

## SEARCH-07 — мобильный выбор и доступность

- Один сценарий на desktop, узком mobile и релевантной промежуточной ширине:
  фильтр → источник → раскрытие → конкретный тур → возврат, затем новый поиск.
- Проверить клавиатуру/focus, название и смысл кнопок, длинные названия/суммы,
  disabled/loading/error, сохранность введённого и отсутствие overlap/overflow.
- Синтетический Chromium, реальный mobile и физический Safari — разные evidence.
  Блокировку browser URL не обходить; доступную проверку не выдавать за недоступную.
- Готово: подтверждённые дефекты исправлены в существующем owner без stacked CSS;
  непроверенные платформы перечислены в release gate, exact artifact указан.

## SEARCH-08 — измерять качество без массовых поисков

- На фиксированном корпусе сохранённых ответов считать accepted unique hotels,
  retained/visible/reachable offers и причины отсева. Сегментный поиск из прошлого
  не повторять и не приписывать внутреннюю причину неполноты Tourvisor без доказательств.
- Локально измерять projection/filter/render; в разрешённом probe — только доступные
  фактические timings/request counts. p50/p95 не сообщать по 1–2 поискам.
- Выбрать один измеренный bottleneck/потерю, исправить без лимитов наугад; сравнить
  те же входы. Кеширование/виртуализация допустимы только после доказанного сценария,
  с invalidation generation и сохранением доступности всех предложений.
- Выход: baseline, один diff, сохранность offers, начальный/полный JS/CSS delta,
  проверенные timings и ограничения выборки. Никакого автоматического mass top-up.

## SEARCH-09 — подключение Андромеды

Это принимающая часть INT-12 для Андромеды: один общий пакет, не повторная интеграция.

- Только после INT contract/adapter и verified identities. Reuse SEARCH-05/06 contract
  и общий renderer; не создавать отдельный третий набор карточек/фильтров/выбора.
- Проверки: TV+ANEX+Andromeda с одинаковыми числовыми provider IDs, partial failure,
  разные currencies/finality и неизвестное питание. Unsupported offer selection
  отключён адресно; остальные источники продолжают работать.
- Готово: подтверждённое покрытие capabilities, один общий preview, budgets из договора
  Андромеды, действующий выключатель/rollback провайдера. Production — отдельный release gate.

## Измеримый результат направления

На одних сохранённых данных: 0 потерь допустимых offers, 0 ошибочных склеек по имени,
0 stale-generation подмен, 0 лишних supplier-запросов от локальных действий;
выбранный тур сохраняет provider/search/offer context. Эти значения — критерии тестовой
приёмки, не заявление об уже измеренном идеальном production.

Завершение каждого пакета: existing issue + source/checked/published/deferred;
следующий свободный пакет выбирается из зависимостей, а не запускается повтор готового.
