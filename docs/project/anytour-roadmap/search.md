### OTA-2 / S3_OTA_SELECTED_OPTIONS — выбор условий и уверенность в цене

- **Польза:** сравнить реально доступные номер/питание/размещение/рейс, увидеть различия
  и итог без длинного повторяющегося описания над действием. Подробности отеля раскрываются.
- **Владение:** canonical `v2/tour-controller-v4.js`, summary-cta и results-layout;
  один writer, существующий выбор варианта из renderer. При необходимости сначала
  read-only проверка доступности variants, затем bounded change, без новых price formulas.
- **Готово:** тур A → допустимый вариант B → рейс → телефон сохраняют выбранные ID,
  поля и цену; возврат сохраняет локальные фильтры/позицию. Сравнение цены допустимо
  только для сопоставимых туристов/дат/ночей/валюты; различия условий явно показаны.
- **Unknown:** отсутствующие сборы/багаж/рейсы/подтверждение не превращаются в ноль
  или «включено». Заявка не является гарантией цены/брони. #1685 — поставщик входов,
  не разрешение SEARCH исправлять арифметику или внешний lead contract.

### OTA-3 / S3_OTA_SHORTLIST_COMPARE — короткий список 2–3 вариантов

- **Польза:** сравнить понятные различия и вернуться к выбору без регистрации.
  Перед реализацией проверить живые owners: переиспользовать действующее сохранение,
  если оно существует, retired comparison slots не активировать автоматически.
- **Объём:** локальный список и сравнение двух/трёх вариантов, без сервера аккаунтов,
  рассылок или записи персональных данных. Новый owner при необходимости явно
  зарегистрировать в README/manifest; одна реализация состояния/контролов.
- **Контракт:** hotel bookmark отдельно от offer snapshot; accepted hotel ID и
  provider/search/offer identity, критерии и observedAt сохраняются по доступным полям.
  В локальное хранилище не писать телефон, имя, токены или полный raw payload.
- **Готово:** добавить/удалить/очистить/перезагрузить; storage unavailable/corrupt
  не ломает поиск. Новый search generation инвалидирует действия старого offer.
  Сохранённая цена помечена временем и не считается актуальной. Проверка доступности
  только явным действием через существующий разрешённый путь, не скрытыми поисками.
- **Зависимости:** TV-only первый этап возможен без #1731; новый provider подключается
  только по готовому контракту. Нельзя при открытии bookmark подставить похожий тур.

## SEARCH-02 — один контекст конкретного предложения

- Польза: цена, номер, питание и источник выбранного тура не подменяются соседним туром.
- Входы: сохранённые broad TV, point-TV и ANEX raw/projected fixtures; текущий selected
  и внешний lead contract. INT отвечает за source identity, SEARCH — за UI-состояние.
- Описать внутренний envelope: generation, provider, providerSearchId, offerKey,
  supplierHotelId, acceptedLocalHotelId, criteria snapshot, observedAt, price/currency,
  условия пакета и признак неизвестных сведений. Это проектируемые внутренние поля;
  реальные имена и доступность подтверждаются источником, не выдумываются.
- Отдельно: общий broad searchId остаётся своим; point searchId принадлежит только
  point-оферам. Недоступное offerKey нельзя заменить hash от похожей цены и объявить
  бронируемым идентификатором. Источник API отдельно от туроператора.
- Готово: таблица legacy→internal полей, неизвестные поля, immutable fixture, правила
  возврата/new generation/expiry и принимающий owner. Ничего не записано в внешний lead.
- Проверка: одинаковые числовые ID разных источников не коллидируют; offer identity
  не меняется от сортировки/фильтра, ответ старой generation игнорируется.

- Приёмка: выбрать point-тур A, изменить допустимый вариант, вернуться, выбрать broad B;

  render/filter/reveal не создают запросов. Live — только если остался конкретный риск.
- Откат: отключить новый выбор прежним comparison path, сохранить полученные предложения.

## SEARCH-04 — выбор ANEX и состав цены

- Вход: INT сохраняет доказанный offer/search context и поля цены; состав доплат
  проверяет отдельный владелец #1685. Отсутствие ответа не превращать в «всё включено».
- Компоненты: INT `v2/api-anex-search3-preview.php`; SEARCH выбранный тур/summary.

## SEARCH-05 — единый тестовый поиск

Это принимающая часть INT-12: один общий PR/owner и один цикл приёмки, не два переноса.
INT-06 и SEARCH-02/04 — producer/consumer одного контракта, без двух конкурирующих DTO.

- Вход: bounded INT→SEARCH handoff с exact source/destination SHA, DTO/fixtures,

- Портировать функцию, а не старый UI: один accepted local ID → одна карточка;

- Готово в тесте: TV-only/ANEX-only/both, source errors, no mappings, cross-generation;
  точные counts на одном наборе сохранённых входов, 0 дублей по accepted ID,
  все допустимые offers доступны. Старые результаты не считаются новым приростом.
- Публикация: fresh release exact artifact в common preview, rollback к его предыдущему

## SEARCH-06 — сохранность при независимом поступлении данных

- Проверять изменённый общий шов, а не переделывать уже готовые own-preview фильтры.
- Матрица: TV раньше/позже ANEX, ANEX timeout после TV success, empty, duplicate response,
  late previous generation, filter-before-complete, zero filtered offers и reset.
- Питание и бюджет применяются к одному предложению; minimum/count/calendar происходят
  от той же выборки. Неизвестный рейтинг/питание не угадывать; неполный facet не обещать.
- Готово: raw сохранён, проекция детерминирована, sorting/reveal/return не теряют туры;
  одна ошибка не обнуляет другой источник, max limits прежние, suppliercalls от фильтра0.
- Откат ограничен новой интеграционной проекцией; контракты и источники не переписывать.

## SEARCH-07 — мобильный выбор и доступность

- Один сценарий на desktop, узком mobile и релевантной промежуточной ширине:

- Готово: подтверждённые дефекты исправлены в существующем owner без stacked CSS;
  непроверенные платформы перечислены в release gate, exact artifact указан.

## SEARCH-08 — измерять качество без массовых поисков

- На фиксированном корпусе сохранённых ответов считать accepted unique hotels,
  retained/visible/reachable offers и причины отсева. Сегментный поиск из прошлого
  не повторять и не приписывать внутреннюю причину неполноты Tourvisor без доказательств.
- Локально измерять projection/filter/render; в разрешённом probe — только доступные
  фактические timings/request counts. p50/p95 не сообщать по 1–2 поискам.
- Выбрать один измеренный bottleneck/потерю, исправить без лимитов наугад; сравнить
  те же входы. Кеширование/виртуализация допустимы только после доказанного сценария,
  с invalidation generation и сохранением доступности всех предложений.
- Выход: baseline, один diff, сохранность offers, начальный/полный JS/CSS delta,
  проверенные timings и ограничения выборки. Никакого автоматического mass top-up.
