# Модели для разработки AnyTour

Выбор от 2026-09-09. Это рабочая рекомендация по задачам разработки, а не добавление
LLM в пользовательский поиск, расходы на новый API или установка плагинов.
Четыре направления не требуют четырёх разных моделей или постоянных веток.

## Что подтверждено

Официальная [страница моделей OpenAI](https://learn.chatgpt.com/docs/models) описывает
GPT-6 Astra как наиболее способную модель для сложной работы; GPT-5.6 Sol — для
сложных задач кода и исследования; Terra — сбалансированный вариант повседневной
работы; Luna — быстрый и более доступный вариант семейства. Высокий reasoning требует
больше времени/токенов. Названные модели также доступны для делегирования в этой сессии.
Прайс, квоты аккаунта и модель каждого фонового запуска отдельно не проверены.

Распределение ниже — наша инженерная рекомендация, а не измеренный benchmark AnyTour.

## Небольшой основной набор

| Роль | Модель | Reasoning | Какие работы поручать |
| --- | --- | --- | --- |
| ARCH — архитектура/координация | `gpt-6-astra` | high; xhigh для неоднозначного стыка | Границы провайдеров, migrations/auth/identity, последовательность интеграции, разбор сложного блокера |
| BUILD — основная разработка | `gpt-5.6-sol` | medium; high для нескольких связанных компонентов | API adapter, state/lifecycle, importer/panel, выбор тура, сложная диагностика и узкие регрессии |
| BUILD-L — ограниченная повседневная реализация | `gpt-5.6-terra` | medium | Проверенные шаблоны страниц, локальный UI по готовому контракту, небольшие PHP/JS исправления, документы |
| REVIEW — независимое ревью | `gpt-6-astra` для data/auth/context; `gpt-5.6-sol` для обычного PR | high | Проверка diff против инвариантов, конкуренции, полноты и критериев; отдельный контекст от автора |
| ASSIST — вспомогательная работа | `gpt-5.6-luna` | low/medium | Read-only перечни файлов/ссылок, таблицы фактов из предоставленных данных, черновики checklists/fixtures |

GPT-5.5 не нужен как отдельная обязательная роль. Если нужная модель недоступна,
задача получает явную замену из доступных, с сохранением границ и проверок.
Ревьюер не становится независимым только из-за другой марки модели: ему нужны
исходные требования, diff и evidence, а не только пересказ автора.

## Назначения по направлениям

| Направление | Ведущий | Реализация | Помощник | Где усиленное ревью |
| --- | --- | --- | --- | --- |
| INT / ANEX / Андромеда | Astra high | Sol high на auth/DB/identity; medium на изолированном adapter | Luna читает схемы/перечни без записей | Запись manual decisions, pair exclusions, migration/import, price/offer contract — Astra high |
| SEARCH | Astra high на общем контракте, Sol на исполнении | Sol medium/high | Terra для локального представления по готовой спецификации | generation/searchId/offerId/selected и handoff — Astra; обычный UI — Sol |
| SITE | Sol medium | Terra medium, Sol при shared shell/handoff | Luna для инвентаризации контента | Переходы к поиску/общие компоненты — Sol; архитектурная передача — Astra |
| SEO | Astra high на структуре/индексации | Sol для policy/data logic, Terra для утверждённых текстов/шаблонов | Luna для группировки проверенных URL | canonical/robots/redirects/schema data — Astra; публикация всё равно требует действующего допуска |

SEO-тексты любой модели проверяются по фактам/источникам. Не выдумывать отзывы,
рейтинг, цены, наличие туров, юридические условия или особенности отеля. LLM не решает
соответствие ANEX→local по похожему названию: действуют existing strict/manual правила.

## Как выбирать усилие и не перегружать работу

1. По умолчанию ограниченный пакет получает Sol medium либо Terra medium для SITE/docs.
2. Сложный state, две системы ID, auth/DB-конкуренция — Sol high и независимое ревью.
3. Неясный контракт, архитектурный конфликт или повторный содержательный провал —
   Astra high/xhigh с конкретным вопросом и исходными evidence.
4. Max/Ultra не включаются на каждый PR. Делегировать можно только независимую часть,
   пока основной исполнитель делает полезную работу. Не раздавать один файл нескольким writers.
5. Luna не принимает критические записи, не выбирает автоматические hotel bindings,
   не утверждает security/deploy и не заменяет основной review.
6. Отсутствующие права, supplier contract или owner authority не исправляются более
   дорогой моделью. Сохранить блокер и продолжить независимый разрешённый пакет.

Рекомендуемая организация: один координатор, до двух независимых реализаций из
существующих рабочих направлений и временный reviewer/reader по необходимости.
Это лимит организации работы, не утверждение о тарифных квотах. На один файл/DB batch/
preview route остаётся один writer. Не создавать ещё четыре одинаковых автозапуска.

## Проверка полезности выбора

На первых реальных пакетах записывать модель/effort, тип задачи, выполненные acceptance,
повторные исправления, время до проверенного результата и доступный расход. Не запускать
дорогой отдельный турнир на production/поставщиках. На одинаковых сохранённых fixtures
более лёгкая модель пригодна, если выдерживает те же критерии без роста переделок.
Для критического writer обязательные проверки не сокращаются из-за уверенности модели.

## Что настроено, а что является планом

Этот файл задаёт рекомендуемые роли. Он сам не меняет модель текущего чата или уже
запущенного задания. Две существующие автозадачи читают центральный план; выбор модели
их основного запуска не считается изменённым без подтверждённой настройки/readback.
При новом делегировании модель можно назначить доступным механизмом и записать факт
в задаче; при невозможности используется текущая модель с честным указанием.

Новые сторонние модели/подписки/плагины сейчас не нужны для этих планов.
Пересматривать выбор после реального изменения доступности либо обнаруженного риска,
не при каждом запуске. Официальный источник проверять заново перед сменой настроек.
