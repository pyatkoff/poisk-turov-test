# SITE — подробный план развития сайта AnyTour

План направления [#1719](https://github.com/pyatkoff/poisk-turov-test/issues/1719). Координатор — #996; правила владения — [anytour-development.md](../anytour-development.md). База — `release/search3-production-ready-v1`, проверенная при составлении версия `cf3f4b6fc0a1b82b7e6b4f3e3ae6818c5d198c90`, 9 сентября 2026. Это последовательность ограниченных пакетов, а не разрешение одновременно менять все перечисленные файлы. Перед исполнением — свежие head, AGENTS, OWNER_PRIORITY, `AUTOPILOT_STATE.json.current_task`, открытые PR/CI и claim точных файлов в #996.

## Результат для посетителя и текущая основа

Посетитель понимает, где выбрать направление, получает правдивые сведения и переходит в поиск с нужными параметрами. Главная, направления и служебные страницы выглядят как один сайт, работают с телефона и не теряют путь к выбранному туру. SITE не создаёт вторую выдачу или собственный механизм заявки.

Уже есть общая оболочка, country/resort/month/hotel-шаблоны, изолированный whole-site preview и переходы в Search3. Последний подтверждённый опубликованный общий source — `840cd2793932e67e0377f5bfc13b325ad4801569`, artifact `10097233750`, deploy `34335163839`, evidence `10097405094`. Снимок не заменяет свежую проверку публикации. Desktop главная → календарь → selected → форма проверен, заявок не отправляли. Live mobile/физический Safari и полный site review не объявлены завершёнными.

Активная продуктовая задача — `S3_PRODUCT_CURRENT_ACCEPTANCE`; её известный дефект `м&#178;` принадлежит SEARCH display owner (`v2/tour-controller-v4.js`). SITE передаёт найденный пример владельцу SEARCH, не создаёт параллельный фикс. Форма, календарь, фильтры и ранее принятый handoff не становятся новой очередью тестирования. Существующий утверждённый дизайн сохраняется; старые DS2 runtime-слои отключены и не возвращаются из ANEX-основы.

## Границы и модельные роли

SITE владеет `v2/site-page-shell-v1.php`, `site-header-v2.*`, `site-footer-v1.*`, `home-v1.php`, `home-entry-v1.php` и согласованными route templates/стилями. `v2/site-path-v1.php`, `offer-freshness-v1.php`, country/resort/month-шаблоны — совместные контракты: один writer SITE, входные требования SEARCH/INT/SEO. Поисковые lifecycle/results/selected/lead остаются SEARCH; supplier/data/accepted ID — INT; metadata/indexability policy — SEO.

Модельные роли связываются с конкретными моделями в [общей матрице](models.md): ARCH проектирует границы и сложный межмодульный пакет; BUILD реализует; REVIEW независимо проверяет поведение и границы; ASSIST собирает карту/данные/документацию. На каждый пакет один BUILD writer; дополнительный REVIEW не означает второй кодовый PR. Результат ревью содержит конкретные дефекты и ограничения, а не формальное одобрение.

## Пакеты исполнения

### SITE-01 — закрыть оставшиеся сценарии текущей приёмки

- **Статус/зависимость:** ready после сверки активного current_task и занятых файлов; сначала без правок. Не повторять уже подтверждённый desktop путь без нового риска.
- **Польза и объём:** посетитель может открыть меню, прочитать содержимое и перейти в поиск с телефона. Один representative путь главная → существующее направление → поиск, плюс конкретный responsive участок из текущего deferred. При доступном устройстве отдельно Safari; эмуляцию не выдавать за физическое устройство.
- **Вход/выход:** published source/artifact и сохранённая приёмка → короткая матрица `маршрут/состояние/viewport/browser → passed/defect/deferred` с воспроизводимым примером. Найденный дефект либо устраняется одним пакетом в текущем владельце, либо адресно передаётся SEARCH.
- **Владение:** SITE shell/navigation; `src/search3` и `tour-controller-v4.js` только по handoff SEARCH. Роли ASSIST + BUILD; REVIEW — изменённое состояние.
- **Приёмка/узкие проверки:** меню/CTA доступны мышью и клавиатурой, фокус виден, текст и кнопки не перекрываются, переход остаётся внутри preview и сохраняет критерии. Проверять только релевантные ширины и intermediate breakpoint. Нет изменений API/заявок и нового live supplier search ради снимка. Изменённый код проходит применимые Security/owner/isolation; docs-only не строятся.
- **Откат:** revert только подтверждённого исправления; при публикации штатно восстановить предыдущий exact preview artifact. При недоступной проверке — deferred, а не обход ограничения.

### SITE-02 — единая и правдивая навигация

- **Статус/зависимость:** ready для адресного аудита; реализация после SITE-01 либо независимо в незанятом owner.
- **Польза и объём:** одно понятное действие для поиска/помощи; посетитель не попадает в соседний preview, тупик или несуществующую страницу. Один связный набор header/footer/menu, без нового визуального концепта.
- **Вход/выход:** фактически подключённые shell/templates и разрешённый список ссылок → исправленный navigation model в существующих владельцах, список изменённых ссылок и их назначения. Уже корректные ссылки не переписывать.
- **Владение/роли:** `site-header-v2.*`, `site-footer-v1.*`, при необходимости `site-page-shell-v1.php`/`site-path-v1.php`; SITE BUILD, REVIEW; SEARCH согласует ссылку в поиск, SEO — семантическую иерархию.
- **Приёмка/проверки:** внутренние пути корректны в production-mode fixture и preview-mode fixture; helper prefix идемпотентен; внешние телефоны/ссылки не преобразуются; canonical не переписывается навигационным helper. Одна keyboard/mobile проверка изменённого меню, отсутствие повторных handlers и overflow. Контакты/часы берутся из существующего проверенного источника.
- **Откат:** revert конкретных shared owner changes; старый маршрут остаётся доступен. Redirect/robots/canonical/production sitemap в этот пакет не входят.

### SITE-03 — точный переход со страницы в поиск

- **Статус/зависимость:** после SITE-01; контракт SEARCH обязателен до изменения общего helper. Сначала найти конкретный пробел в существующей матрице handoff, не строить её заново.
- **Польза и объём:** выбранные страна/курорт/отель/месяц не теряются и не подменяются. За пакет один тип страницы и один подтверждённый пропуск/пограничное состояние.
- **Вход/выход:** `docs/project/search3-site-handoff-owner.json`, реальная source state и existing handoff URL → согласованный пример `page state → search state`, исправление в текущем owner и regression fixture. ID только принятые/разрешённые соответствующим контрактом; marketing label не превращается в supplier ID.
- **Владение/роли:** SITE `site-path-v1.php` и relevant renderer; SEARCH владеет parsing/defaults/lifecycle (`v2/index.php` и действующие helper). ARCH на контракте, один BUILD по объявленным путям, REVIEW.
- **Приёмка/проверки:** страна/курорт/accepted hotel ID/даты/ночи/состав сохраняются там, где заданы и поддерживаются; ошибочные/просроченные данные не превращаются в обещание доступности. Переход до готовности каталога не стартует неверный поиск. Узкая fixture на выбранный page type, malformed input и preview prefix; без изменения внешнего Tourvisor URL/payload.
- **Откат:** restore прежнего внутреннего преобразования одной страницы, без изменения источника данных, search engine или launch policy.

### SITE-04 — понятная свежесть и отсутствие предложений

- **Статус/зависимость:** готов к анализу после назначения SITE/INT владельцев; меняется только подтверждённый сценарий.
- **Польза и объём:** посетитель различает сохранённую цену и реально выбранный тур; страница остаётся полезной без свежего предложения. Одна family, например hot или monthly, и её empty/stale/current состояния.
- **Вход/выход:** сохранённые snapshots с timestamp и `offer-freshness-v1.php` → видимое правдивое состояние, корректное действие в поиск и narrow regression. Новые supplier запросы/сборщики не создаются ради этого пакета.
- **Владение/роли:** SITE отображение и relevant renderer; INT отвечает за смысл snapshot/source/timestamp, SEARCH — свежий поиск. BUILD + REVIEW; ARCH только если найдено расхождение контрактов.
- **Приёмка/проверки:** прошедший вылет не рекламируется как текущий; month window остаётся в выбранном месяце и существующем business clock; отсутствующая цена не подменяется нулём; no-offer не объявляется отсутствием самого отеля. Срок хранения кэша не равен bookability. `tests/offer-freshness-smoke.php` и адресные фиксированные даты/empty fixtures, визуально один затронутый state.
- **Откат:** revert display policy change, сохранить raw snapshots и общие API/price arithmetic.

### SITE-05 — содержательная эталонная страница

- **Статус/зависимость:** после SEO-01/SEO-02 и согласованного источника фактов. Один существующий тип и 1–3 уже разрешённых примера; выбор типа по данным, а не по числу потенциальных URL.
- **Польза и объём:** пользователь получает ответ о направлении/курорте/отеле и понятный следующий шаг. Новая разметка не нужна, если текущий renderer уже покрывает сценарий.
- **Вход/выход:** SEO brief с intent/фактами/источниками/доступными ссылками → корректно заполненный текущий template; пустые разделы отсутствуют или объяснены. Изображения имеют честное происхождение и fallback; тексты plain text/escaped. Не выдумывать рейтинг, «лучший сезон», цену, преимущества, услуги, юридические или платёжные условия.
- **Владение/роли:** SITE relevant country/resort/month/hotel renderer и существующие shared styles; SEO задаёт content brief, INT подтверждает источник. ARCH выбирает минимальный объём, BUILD + REVIEW; ASSIST может подготовить sourced draft.
- **Приёмка/проверки:** факт связывается с сохранённым источником и датой; нет повторного шаблонного текста под видом индивидуальной информации; CTA переносит только обещанные параметры. Один complete и один missing-content render fixture, escaping/URL validation, keyboard и mobile/desktop изменённой области. Нет нового автоматического mapping.
- **Откат:** revert контент/renderer одной family; не удалять существующие production URL или менять их indexability.

### SITE-06 — доступность и скорость подтверждённого участка

- **Статус/зависимость:** после representative page; не является поводом для общего refactor или новой CSS-системы.
- **Польза и объём:** быстрее первая полезная информация и меньше визуальных скачков; действия доступны с клавиатуры. Один измеренный дефект: image geometry, focus order, скрытый блок, повторный handler или лишняя блокировка.
- **Вход/выход:** воспроизводимое наблюдение на одной странице → исправление текущего владельца с before/after evidence. Сначала измерить, затем выбрать работу; если дефекта нет, пакет не создаётся ради счётчика.
- **Владение/роли:** SITE styles/template; assets Search3 только через SEARCH и `src/search3/manifest.json`. BUILD, независимый REVIEW; ASSIST собирает измерения.
- **Приёмка/проверки:** выбранный дефект устранён; нет нового overflow/скрытого контента/сломанных ссылок, source attribution сохранена. Initial/full/inline CSS/JS дельта фиксируется честно; network/viewport одинаковы для сравнения. Полевые web-vitals не заявляются по одному синтетическому прогону. Узкая поведенческая/визуальная проверка и применимые guards; один build при изменении generated assets.
- **Откат:** revert узкого изменения; previous exact artifact остаётся доступен. Lazy loading или перенос кода не выдавать за удаление веса.

### SITE-07 — единая тестовая версия и подготовка переноса

- **Статус/зависимость:** когда накоплен полезный checked пакет SITE/SEARCH. Не ждёт всего каталога ANEX или Андромеды; интеграции входят отдельными принятыми пакетами.
- **Польза и объём:** владелец смотрит одну актуальную общую тестовую версию, а не ищет, какая ветка содержит нужную функцию.
- **Вход/выход:** совместимые source PR и exact artifact → release checklist по конкретным маршрутам, published source/artifact, diff к прошлому preview, deferred и rollback manifest. Свежий release получает bounded INT handoff; старую ANEX-основу не накладывать целиком.
- **Владение/роли:** координатор выпуска + SITE/SEARCH owners; ARCH сводит зависимости, REVIEW проверяет согласованность. Один publisher на whole-site route; активный deploy не дублировать.
- **Приёмка/проверки:** exact provenance/readback, noindex, disabled production leads/counter0 и production fingerprints сохранены. Проверить изменённые страницы и один затронутый переход; весь journey только при реальном межмодульном риске. Все docs-only накопления используют существующие evidence, без deploy.
- **Откат:** восстановление предыдущего проверенного preview artifact штатным manifest; main/production не меняются. Итог явно `preview-published`, не `production-approved`.

### SITE-08 — одобренная миграция и проверка результата

- **Статус/зависимость:** blocked до явного визуального одобрения владельцем конкретной версии в #1334. До этого можно полностью подготовить reviewable diff, сценарии и rollback.
- **Польза и объём:** на основной сайт попадает проверенный общий продукт с сохранёнными рабочими маршрутами и заявками. Это отдельный выпуск, не автоматический побочный эффект завершения SITE-07.
- **Вход/выход:** approved exact source/artifact/routes и предусмотренная штатная процедура → запись результата публикации/проверок и rollback point. Legal/payment неопределённости не переносятся как готовый контент.
- **Владение/роли:** координатор releases, SEARCH/SITE по своим компонентам; ARCH готовит sequence, REVIEW проверяет конкретные защищённые границы.
- **Приёмка/проверки:** применимые production gates, маршруты/HTTP/содержимое и существующий lead contract проверены по правилам проекта; неподтверждённые реальные заявки не имитируются отправкой. Отдельные изменения SEO indexation не следуют из UI approval. Даты и конкретный source отделены от прежних checks.
- **Откат:** заранее проверенная штатная процедура на предыдущую production версию, с сохранением данных/принятых связей. После утверждённого выпуска наблюдать ошибки и существующие показатели, не менять Метрику/goals.

## Очередность и измерения

1. SITE-01 и SEO-01 можно выполнять параллельно read-only; текущий SEARCH current_task имеет свой writer.
2. SITE-02/03/04 — только по подтверждённому пробелу; выбрать один, не открыть одновременно три PR на общие файлы.
3. SITE-05 следует за brief SEO и данными INT; SITE-06 — за измеренным дефектом. SITE-07 собирает готовые небольшие части, SITE-08 остаётся отдельным допуском.

Измеряем: число реально проверенных переходов и их провалов; потери параметров по fixture/live evidence; broken links в bounded наборе; доступность основных действий клавиатурой; overflow/CLS и вес изменённой страницы в сопоставимых условиях; долю карточек со сведениями только при известном знаменателе. Конверсию/полевую скорость брать из уже разрешённых источников, с периодом, route и устройством; при отсутствии данных ставить `not_measured`, не придумывать проценты или сроки роста. Число PR не является результатом для пользователя.

В issue/state каждого активного пакета хранить baseline, owned paths, источник фактов, implemented/checked/preview-published/production-approved, exact SHA/artifact, deferred и один следующий доступный шаг. Этот план не дублирует исполняемый `current_task` и не превращает исторические DONE в новый backlog.
