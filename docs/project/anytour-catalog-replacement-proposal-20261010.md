# Полная замена каталога AnyTour — проект перехода

Дата: 10.10.2026. Статус: **DESIGN_DRAFT / DEPENDENT_SCOPE_NOT_ADMITTED / NOT_EXECUTABLE**.

Поручение владельца: «ну создавать заново, наполнять данными и переносить соответствия».
Цель — заменить внутреннее хранилище каталога, перенести накопленные данные и решения,
затем отдельно заполнить подтверждённые пробелы и переключить потребителей.
Этот документ фиксирует проект перехода. Новый каталог, схема, перенос и наполнение не реализованы.

Проверенная исходная версия кода: release `725b75d809c5acece271e14c5ff52fe75f249bb9`;
контрольная main `640a80c7aff2c965c79972a53b1cfe3568f2840d`.
Это source review: текущее содержимое БД, полнота данных и схема runtime не проверялись.
Действующие [архитектура](../../ARCHITECTURE.md), writers и каталог сохраняют свой статус.
Предложение не вводит второго активного владельца одной и той же карточки.

## Целевая модель и сохранение идентичности

Одна подтверждённая физическая гостиница имеет один собственный canonical ID, карточку
с названием, описанием, упорядоченными фотографиями и фактами, ревизию и происхождение значений.
Идентификаторы legacy/local, TV и других поставщиков хранятся отдельно, со своим namespace.
Совпадение чисел, названий или адресов не доказывает соответствие гостиниц.

Предлагаемый вариант перехода — **сохранить действующие own IDs** в новом хранилище.
Старый номер нельзя присвоить другой гостинице. Если дальнейший review выберет новые номера,
понадобится полная проверяемая old→new карта и совместимость всех зависимых ссылок;
такая перенумерация здесь не предлагается к исполнению.
Merge/split гостиниц требует отдельного решения с доказательствами, без автоматического объединения по имени.

## Что переносится

| Состав | Требование сохранения |
| --- | --- |
| Canonical profiles | Исходные profile JSON/hash, own ID, revision, active flag, timestamps; ручные значения, непустые поля и порядок фотографий |
| Source identities | Точные байты namespace/external key, target, acquisition kind, source JSON/hash, first/last seen; числовые ключи не смешиваются |
| Provenance | Raw cards, status/hash/fetched time, доступная цепочка происхождения, receipts и before-images; отсутствующая история остаётся неизвестной |
| MATCH | Accepted/manual и rejected/excluded/revoked/conflict/pending решения, evidence, supersession и приоритет/veto; перенос связи не является новым acceptance |
| Зависимости | Offers и их expiry/context, provider/local references; hotel-scoped room/meal concepts с ID/facts/revision/active; stay/room/meal mappings со state/evidence/reviewer; revision-bound search-meal membership и все FK |
| Потребители | Hotel URL, избранное, autocomplete, canonical hydration, календарь и восстановление выбранного тура; own ID не подставляется в supplier/search/offer/lead ID |
| История операций | Состояния STOP, UNKNOWN, consumed и исключения вместе с доказательствами и исходными идентичностями; перенос не возобновляет операции |

Описательные roomTypes/meals из карточки не становятся подтверждёнными справочниками предложения.
Перенос старого offer не делает его свежим или пригодным для бронирования.
Сохранение карточек и получение нового содержимого — разные этапы: копирование не доказывает freshness источника.
Допуск миграции не разрешает collector или новые content writes: наполнение требует отдельного admission
и проверки integrity/freshness источников.

Consumer parity включает всю цепочку autocomplete `catalog_hotels + hotel_aliases → legacyHotelIds → own hydration`
и legacy IDs для exact refresh/calendar. Canonical endpoint/isolation и строгий DTO
(`source`, `catalog`, `revision`, `links`, requested/missing IDs, fail-closed ошибки)
сохраняются либо отдельно согласованно адаптируются до переключения.

## Нужный состав доказательств для будущего переноса

До реализации переноса нужен полный согласованный private snapshot перечисленных сущностей,
с границей консистентности, manifest/digests, учётом зависимых записей и проверенной восстановимостью backup.
Пакет должен включать состояния MATCH, ручные решения и историю операций, а не только положительные связи.
Это требование к будущему review; документ не создаёт и не разрешает exporter или получение private bundle.

Публичный DTO не подходит как полный backup/export: он показывает только active projection,
фильтрует фотографии и не содержит полного состава source identities, MATCH, provenance и служебных полей.
Отсутствующий manifest или незаписанный scope нельзя трактовать как пустую историю.
Для phase3 сохраняется UNKNOWN_NO_REPLAY до отдельного доказательного решения.

Полная замена потенциально включает ранее остановленные и уже обработанные гостиницы.
**Новые ID, таблицы, БД и названия операций не сбрасывают ограничения**: они следуют за идентичностями
и исходными доказательствами. Полную замену нельзя объявить независимой партией.

## Этапы и критерии перехода

| Этап | Проверяемый результат | Текущее состояние |
| --- | --- | --- |
| 0. Review проекта | Согласованный состав, сохранение ID и решений, зависимости и критерии перехода | Этот документ; исполнение не допущено |
| 1. Проверка модели | Изолированные синтетические fixtures проверяют перенос, неоднозначные связи, manual precedence и неизвестные состояния | Не реализовано; без реальных данных и источников |
| 2. Допуск конкретной миграции | Отдельное рассмотрение platform refusal; разрешённые текущие private evidence; решение по UNKNOWN scopes; target/schema ownership, backups и writers | Не получен; направление владельца не заменяет эти доказательства |
| 3. Подготовка переноса | Review точной схемы/состава, полный crosswalk и FK, сравнение источника и целевой проекции, журнал ожидаемых изменений | Не реализовано; не является командой миграции |
| 4. Проверяемый перенос | После допуска — перенос в изолированное целевое хранилище с сохранением исходной идентичности и истории | Не выполнен; существующий каталог остаётся активным |
| 5. Отдельное наполнение | Только рассмотренные exact sources и пробелы, защита ручных/непустых значений, revision/hash CAS и atomic provenance | Не выполнено; старые collector/recovery операции не повторяются |
| 6. Readback и потребители | Подтверждённые результаты записи, hashes/связи/FK, URL/избранное/поиск/offer/stay parity, desktop/mobile сценарии | Не проверено; source CI не заменяет runtime acceptance |
| 7. Переключение и возврат | Один authoritative writer, согласованный порядок readers, сохранённый старый каталог и проверенный rollback | Не подготовлено к исполнению |

Этапы 2–7 описывают зависимости будущего решения, а не очередь разрешённых запусков.
При cutover нужен единый writer; параллельные независимые authoritative writers недопустимы.
Rollback должен учитывать изменения после переключения: возврата старого reader для этого недостаточно.
Старые карточки, mappings и доказательства сохраняются; автоматические drop/truncate/reset не предусмотрены.

## Приёмка будущей реализации

- Полный учёт записей/решений/зависимостей; ID сохранены либо имеют полную проверяемую карту идентичностей. Исходные source bytes/hash сохраняются неизменно; любое преобразование целевого profile имеет собственный digest и доказуемую связь с исходником.
- Сравнение profile/source hashes, revisions, timestamps и ручных значений с исходным snapshot; ни одного orphan FK или молчаливого manual override.
- Сохранение freshness/expiry, отрицательных решений, исключений и UNKNOWN; неизвестные исходы не выдаются за ноль записей или отсутствие ограничений.
- Раздельный фактический учёт переноса и нового наполнения, durable receipts и post-COMMIT readback; CI и HTTP 200 сами по себе не подтверждают результат.
- Проверка поиска, карточки, старой ссылки, избранного, календаря и восстановления выбранного предложения; проверка возврата с сохранением данных после cutover.
